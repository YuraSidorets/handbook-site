    1 Frontend and User Experience

    5.1 Frontend and User Experience¶

    Frontend observability describes the application as it behaves on the user's device. It includes loading content, responding to input, making requests and showing the result of an operation.

    A server can return a correct response while the interface remains unusable. A script may fail before sending a request, the browser may spend too long processing the response, or a layout change may move a control just as the user selects it. These problems need evidence from the client.

    The useful starting point is the action the user is trying to complete. Page and request measurements then help explain what happened along the way.

    Page Performance and Operation Completion¶

    Page loading, interaction responsiveness and completion of a task describe different parts of the experience.

    For example, selecting a search filter might produce this sequence:

    User selects filter
    → progress indicator appears
    → request returns matching items
    → browser processes the result
    → updated list becomes visible

    The progress indicator can appear quickly while the final result takes several seconds. A measurement that ends at the first visual response would miss most of that wait.

    For important actions, define a duration from the action's start until the intended result is available. Also record failure and cancellation outcomes. An action that never completes will not appear in a histogram that records successful completion times alone.

    Core Web Vitals provide standard measurements for aspects of page experience:

    Measurement What it describes Good threshold
    Largest Contentful Paint (LCP) Loading of the largest eligible visible content element 2.5 seconds or less
    Interaction to Next Paint (INP) Responsiveness to qualifying interactions during a visit 200 milliseconds or less
    Cumulative Layout Shift (CLS) Unexpected movement of visible content 0.1 or less

    Field assessment uses the 75th percentile of each measurement, with mobile and desktop evaluated separately. These thresholds come from the Core Web Vitals guidance; they do not define whether an application's business operation succeeded.

    Use the standard measurements alongside application-specific outcomes. A page can have good loading and interaction measurements while displaying the wrong search results or failing to save a change.

    Navigations and Views¶

    A full navigation loads a new document. A single-page application can replace a view without loading another document. The application's route change and the browser's page lifecycle therefore need not have the same boundary.

    Decide what a page or view measurement represents. For example, “product details ready” might end when the product information and required controls are available, rather than when the route name changes.

    Some browsers and collection libraries support soft-navigation measurements for changes within a document. Support and measurement boundaries depend on the browser APIs and library configuration. Do not assume that every route change resets every Core Web Vital. The web-vitals library documentation describes its supported behavior.

    Use stable view names such as product-details or route templates such as /products/{id}. A URL containing a different product, search term or session value for every visit is usually unsuitable as a metric dimension and may expose sensitive information.

    Client Errors and Failed Requests¶

    Client errors explain failures that server telemetry may never see.

    A useful error record identifies the operation or view, frontend release, error type and relevant stack trace. The deployed JavaScript is often compressed or transformed. A source map maps that deployed code back to its source locations, making the error easier to investigate. The map must match the deployed build. See Chrome's source-map explanation.

    Request failures also need a meaning beyond the HTTP status code:

    • A server response can report a technical failure or an expected rejection.
    • A network failure can prevent any response from arriving.
    • A browser restriction can block access to the response.
    • The application or user can cancel the request.
    • The request can succeed while later client processing fails.

    Keep these outcomes distinct when the client has enough information. A missing response does not identify the server as the cause. If the cause cannot be established, preserve an unknown category rather than assigning a misleading explanation.

    Error counts and affected visits answer different questions. One broken view can generate the same exception repeatedly. Ten thousand exception records might therefore represent far fewer than ten thousand affected visits.

    For example:

    Observed visits:                 1,000
Visits with a rendering failure:    40
Rendering-error records:          600

Affected observed visits: 40 / 1,000 = 4%

    The error records provide diagnostic detail; the visit measurement describes the observed impact. Its numerator and denominator must cover the same visits and collection policy.

    Connecting Browser and Server Evidence¶

    When a slow action includes an API request, related browser and server records can show where the delay occurred.

    An instrumented browser can propagate W3C trace context to an API. The receiving service can then continue the trace, connecting its server span with the browser's request span. This requires compatible instrumentation and an appropriate propagation policy.

    For cross-origin requests, the target must also permit the relevant headers through its cross-origin configuration. Same-origin behavior and cross-origin destination settings differ between instrumentation libraries. Check the installed library rather than assuming that every outgoing request carries context. OpenTelemetry's fetch instrumentation documents its configuration.

    Propagate context only to intended destinations. Trace headers are correlation data, not proof of identity or authorization, and incoming values must be treated as untrusted. The W3C Trace Context standard describes the security and privacy considerations.

    A client request span and a server span still measure different intervals. Network transfer and browser processing can occur outside the server span. Some detailed cross-origin resource-timing fields are also unavailable unless the resource server permits their disclosure. See the Resource Timing restrictions.

    Locating a Slow Interaction¶

    Suppose users report that selecting a filter became slower after a frontend release. Server request durations are unchanged.

    A browser performance recording for one affected interaction shows:

    Request and response:          180 ms
Client calculation afterward: 900 ms
Rendering afterward:          120 ms

    In this simplified example, these stages run sequentially and account for 1.2 seconds after the request starts. The client calculation is the largest observed part. The unchanged server measurement is consistent with the problem being outside the server, but it would not locate the delay on its own.

    Inspect the calculation and compare equivalent interactions before and after the release. A browser performance recording can identify long main-thread tasks; a correlated server trace can check whether the selected request had unusual backend work. Google's interaction-performance guidance explains how main-thread work affects responsiveness.

    Keep the conclusion limited to the evidence. One recording establishes what happened in that interaction. Measurements across the affected view and device groups show how widespread the regression is.

    Coverage and Safe Collection¶

    Real-user telemetry represents the visits that successfully report data. Collection scripts can fail, pages can close before export, networks can disconnect, and consent or privacy controls can prevent collection.

    Check reporting volume and browser support alongside the performance measurements. A sudden improvement accompanied by a large drop in reporting visits may indicate lost coverage. A visit without an INP value, for example, may simply have had no qualifying interaction.

    Compare similar populations when evaluating releases. A change in the proportions of mobile devices, browsers or page types can change an aggregate percentile without a regression within any one group. The field-measurement guidance describes useful measurement context.

    Controlled browser tests provide additional coverage for failures that prevent real-user reporting. Test representative loading, interaction and error paths, including failures before the first API call and failures after a successful response.

    Collect diagnostic context deliberately. URLs, error messages, form values, request bodies and screenshots can contain private information. Routine timing and error collection rarely needs the contents of a user's input. Preserve the view, operation and release information needed for investigation while applying appropriate filtering, access and retention controls.
